# CR-LLM-002: OWASP LLM02 - Insecure Output Handling & Sink Execution

| Metadata | Details |
| :--- | :--- |
| **Rule ID** | `CR-LLM-002` |
| **Category** | `SECURITY` |
| **Default Severity** | `CRITICAL` |
| **CWE Mapping** | [CWE-78: OS Command Injection](https://cwe.mitre.org/data/definitions/78.html), [CWE-89: SQL Injection](https://cwe.mitre.org/data/definitions/89.html) |
| **OWASP for LLM** | LLM02:2025 – Insecure Output Handling |
| **Scanner Target** | Java, Python, JavaScript, TypeScript |

---

## 1. Vulnerability Summary
Insecure Output Handling occurs when raw, unvalidated output generated by a Large Language Model is passed directly into sensitive downstream application sinks, such as:
1. **OS Process Execution**: `Runtime.getRuntime().exec()`, `ProcessBuilder`, `os.system()`, `subprocess.Popen()`
2. **Database Queries**: `Statement.execute()`, raw SQL string execution
3. **Dynamic Code Evaluation**: `eval()`, `exec()`, `new Function()`
4. **Web Browser Sinks**: Direct rendering as unescaped HTML / Cross-Site Scripting (`innerHTML`)

Because LLM outputs can be influenced or manipulated by prompt injections, training data poisoning, or third-party web content (in RAG workflows), treating LLM responses as trusted leads to immediate Remote Code Execution (RCE) or complete database takeover.

---

## 2. Insecure Code Example

```java
public class AiDevOpsAssistant {

    public void executeAiRecommendation(String userQuery) {
        String aiGeneratedCommand = llmClient.ask(
            "Generate a shell command to clean up disk space for: " + userQuery
        );

        // VIOLATION: Passing raw LLM response directly into OS command execution sink
        Runtime.getRuntime().exec(aiGeneratedCommand);
    }
}
```

Python equivalent:
```python
# VIOLATION: Executing raw model SQL in database
sql_query = llm.generate_sql(user_prompt)
cursor.execute(sql_query)
```

---

## 3. Secure Remediation Pattern

Never execute raw LLM strings. Instead, utilize **strict schema validation** (e.g. JSON schema / Pydantic models), **structured tool calls** (OpenAI Function Calling), and **human-in-the-loop (HITL)** approval workflows:

```java
public class AiDevOpsAssistant {

    private static final Set<String> ALLOWED_SCRIPTS = Set.of(
        "/usr/local/bin/clean_docker_cache.sh",
        "/usr/local/bin/rotate_logs.sh"
    );

    public void executeAiRecommendation(AiCleanRequest request) {
        // REMEDIATION: Validate against strict whitelist before execution
        if (!ALLOWED_SCRIPTS.contains(request.scriptPath())) {
            throw new SecurityException("Unauthorized script execution requested: " + request.scriptPath());
        }

        ProcessBuilder pb = new ProcessBuilder(request.scriptPath());
        pb.inheritIO();
        pb.start();
    }
}
```

For SQL generation, restrict the generated query to a read-only database replica user with strict row limits and AST validation (using SQL parser AST inspection).

---

## 4. Verification Checklist
- [ ] No outputs from LLM API calls are passed into `Runtime.exec`, `ProcessBuilder`, or `os.system`.
- [ ] LLMs generate structured parameters (JSON schema) rather than executable shell strings.
- [ ] Privileged actions require explicit two-factor confirmation from a human administrator.
