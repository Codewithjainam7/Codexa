# Codexa Memory Management & Streaming Buffer Architecture

This specification details the memory allocation strategies, streaming extraction buffers, garbage collection profiles, and memory limits employed by Codexa to process repositories up to 3 GB within constrained 512 MB to 2 GB JVM footprints (e.g. Render Web Services).

---

## 1. Memory Architecture Overview

Static analysis platforms that load entire zip files or AST trees into memory quickly suffer from `OutOfMemoryError` (OOM) or long Stop-the-World GC pauses.

Codexa achieves predictable sub-512MB RAM utilization using a streaming, zero-heap-buffer architecture:

```
[ Incoming Network Stream ]
          |
          v
[ 64KB Direct NIO Buffer ] ===> [ SecureZipExtractor ] ===> [ Scratch Temp File on Disk ]
                                                                      |
                                                                      v
                                                            [ Single File AST Parse ]
                                                                      |
                                                                      v
                                                            [ Extract Findings & Discard AST ]
```

---

## 2. 64KB Streaming Buffer Extraction

Instead of buffering archives in memory via `ByteArrayOutputStream` or `byte[]`, the `SecureZipExtractor` utilizes small, fixed 64KB transfer buffers:

```java
private static final int BUFFER_SIZE = 64 * 1024; // 64 KB

try (InputStream is = new BufferedInputStream(zipInputStream, BUFFER_SIZE);
     OutputStream os = new BufferedOutputStream(Files.newOutputStream(targetFile), BUFFER_SIZE)) {
    byte[] buffer = new byte[BUFFER_SIZE];
    int len;
    while ((len = is.read(buffer)) != -1) {
        os.write(buffer, 0, len);
        totalBytesExtracted += len;
        // Verify uncompressed quotas dynamically
        verifyQuotas(totalBytesExtracted, totalFileCount);
    }
}
```

### Advantages:
- **Constant Memory Footprint**: Extraction of a 3.0 GB repository consumes only 64 KB of heap memory per active stream.
- **Immediate Disk Staging**: Avoids JVM heap bloating; extracted files reside in temporary OS disk scratch spaces.

---

## 3. AST Lifespan & Garbage Collection

AST objects (especially comprehensive `CompilationUnit` models containing comments, tokens, and node ranges) are ephemeral:
1. A file is read from scratch disk.
2. The AST is generated by `ThreadLocal<JavaParser>`.
3. Rules execute in parallel visitors, producing lightweight `FindingEntity` records.
4. The AST graph reference is released immediately, allowing Young Generation GC sweeps to reclaim memory before Eden space exhaustion.

---

## 4. Recommended JVM Memory Profiles

### Cloud Container Profile (512 MB - 1 GB RAM, Render Free / Starter):
```bash
JAVA_OPTS="-Xms256m -Xmx768m -XX:+UseG1GC -XX:MaxGCPauseMillis=100 -XX:+ExitOnOutOfMemoryError"
```

### High-Throughput Monorepo Profile (2 GB - 4 GB RAM):
```bash
JAVA_OPTS="-Xms1g -Xmx3g -XX:+UseZGC -XX:+ZGenerational -XX:+ExitOnOutOfMemoryError"
```
